# Tether protocol v1 (revision 2)

Tether links one Android phone and one Mac directly: no server, no account, no cloud.
Everything below is implemented twice, independently, and cross-checked with shared test vectors:

| | Android (Kotlin) | macOS (Swift) |
|---|---|---|
| Code | `android/core` | `mac/TetherCore` |
| Vectors | `protocol/vectors/*.json` (generated by `tools/gen_vectors.py`) | same files |

All integers are big-endian. "B64" means base64url without padding.

## 1. Roles and transports

- **Bluetooth LE (always on).** The phone is the GATT **central** (scans with a service-UUID filter and connects); the Mac is the GATT **peripheral** (advertises only while paired or pairing).
  - Service `7E7E0001-5A1D-4C6B-9C0E-7465746865B1`
  - One characteristic `7E7E0002-5A1D-4C6B-9C0E-7465746865B1`: phone → Mac by *write without response*, Mac → phone by *notify*.
  - The phone requests a 517-byte MTU; the fragment size is `MTU − 3` (minimum 20).
- **Wi-Fi fast path (optional).** When both devices share a network (or the Mac joins the phone's hotspot) the phone listens on TCP and advertises `_tether._tcp` over mDNS. It tells the Mac where to connect over the Bluetooth session (§6). Records on TCP are framed as `u32 length ‖ record` (max 2 MiB).
- In both cases the **phone is the Noise initiator** and the Mac the responder.

## 2. Fragments (Bluetooth only)

A record larger than one ATT payload is split into fragments (layout adapted from bitchat's fragment header):

```
u8  version = 1
u16 recordId      (wraps; one record in flight per direction)
u16 index         (0-based)
u16 total
…   data          (up to maxFragment − 7 bytes)
```

Fragments of a record arrive in order (the link is ordered). The reassembler drops a record on any gap, version mismatch, or if it would exceed 128 KiB; a fragment with `index = 0` always starts a new record.

## 3. Records

```
0x01 ‖ step ‖ noise_message      handshake (step = 1, 2, 3)
0x02 ‖ ciphertext                transport (ChaCha20-Poly1305, Noise nonce counter)
0x03 ‖ reason                    close (plaintext; reasons below)
```

Close reasons: `0 normal, 1 untrusted, 2 busy, 3 protocol error, 4 version mismatch, 5 pairing rejected, 6 unpaired, 7 wrong device, 8 timeout, 9 link lost`.

## 4. Handshake: `Noise_XX_25519_ChaChaPoly_SHA256`

- Prologue: `tether/1` on Bluetooth, `tether/1/wifi` on TCP (a Bluetooth handshake can't be replayed onto TCP or vice versa).
- Static keys: one X25519 key pair per install (Android Keystore-wrapped file / macOS Keychain).
- Payloads: message 1 is empty; messages 2 and 3 carry a JSON **Hello**:
  `{"v":1,"name":"Pixel 8","platform":"android","app":"0.1.0","caps":["clip","notif","file"]}`.
  A `v` other than 1 closes with *version mismatch*.
- After message 3 both sides hold the peer's static key. If it is the paired key (or a pending rotated key, §7) the session is **established**. Otherwise:
  - If pairing is not open on this device → close *untrusted*.
  - Otherwise the session enters **verifying** (pairing, §5).
- Heartbeat: `PING` every 45 s of silence, dead after 20 s more. Handshake timeout 15 s; pairing timeout 120 s.
- Handshake recovery (Bluetooth, since 0.1.1): if the phone hears nothing within 3 s of sending message 1, it starts a fresh session and sends a new message 1 (up to 3 times per link). The Mac starts a fresh session whenever a message 1 arrives while it is still handshaking or after its session closed with the radio link still up, so a lost write never wedges the link. Writes that reach the Mac before the phone's subscription is reported are held and replayed. Fragments are capped at 244 bytes (phone requests ATT MTU 247).

## 5. Pairing

Two ways, both on top of an unauthenticated XX handshake:

1. **Numeric comparison.** Both sides show `SAS = u32(SHA-256("tether-sas/1" ‖ handshake_hash)[0..4]) mod 10^6`, zero-padded to 6 digits. Each user confirms; each device sends `PAIR_CONFIRM {}`. Pairing completes when a device has both confirmed locally and received the peer's confirm. `PAIR_REJECT` (or a timeout) closes with *pairing rejected*.
2. **QR (one tap).** The Mac shows `tether://pair?v=1&k=<B64 Mac static key>&t=<B64 16-byte one-time token>&n=<percent-encoded name>`. The phone scans it, connects, and checks during the handshake that the Mac's static key equals `k` (else close *wrong device*). The phone then auto-confirms with `PAIR_CONFIRM {"token":"<t>"}`; the Mac accepts that as its own confirmation only if the token matches in constant time. The token dies when pairing mode closes.

Only one phone is paired at a time; pairing a new one replaces the old.

## 6. Messages (inside transport records)

```
u8  type ‖ u32 headerLength ‖ header (UTF-8 JSON) ‖ body (raw bytes, may be empty)
```

|---|---|---|---|

## 7. Key rotation

Either side may send `KEY_ROTATE` with a fresh public key over an established Bluetooth session. The receiver stores it as the peer's *pending* key (both old and pending are trusted) and answers `KEY_ROTATE_ACK`. On the ack the sender switches its static key; the next handshake uses the new key and the receiver promotes pending → current. An unacknowledged rotation is retried on the next connection.

## 8. Wi-Fi binding

1. Over the established Bluetooth session the phone sends `WIFI_OFFER` with its addresses, port and a single-use 16-byte token.
2. The Mac connects (Bonjour service whose TXT `id` = B64(SHA-256(phone static key)[0..8]) first, then each address), runs Noise XX with prologue `tether/1/wifi`, and must present **the paired static key**: there is no pairing on TCP.
3. The Mac's first transport message is `WIFI_BIND {token}`. The phone admits it in constant time and burns the token; anything else closes the socket as *untrusted*. A bound session that has not bound within 15 s is closed.
4. While Wi-Fi is bound, clipboard and transfers use it; notifications and control stay on Bluetooth. If Wi-Fi drops, transfers fall back to Bluetooth from the last acknowledged offset.

## 9. File transfer

- Sender stages the file, computes SHA-256, and sends `FILE_OFFER`. Receiver answers `FILE_ACCEPT {offset}` (0, or the length of a partial file from an earlier attempt) or `FILE_REJECT`.
- Sender streams `FILE_CHUNK`s (16 KiB on Bluetooth, 64 KiB on Wi-Fi) with a sliding window (4 chunks on Bluetooth, 16 on Wi-Fi) driven by cumulative `FILE_ACK`s.
- After the last byte, `FILE_DONE`; the receiver verifies SHA-256, moves the file into place, and answers `FILE_COMPLETE {ok}`. A checksum failure restarts once from 0, then fails.
- Limits: warn above 20 MiB; files above 100 MiB wait for Wi-Fi (up to 4 GiB). Interrupted transfers resume after reconnect or relaunch.
- File names are sanitised (no path separators, reserved or control characters, or leading dots; long names are shortened).

## 10. Notifications

The phone decides what to forward (per-app allow/block, muted keywords, quiet hours, skip silent/ongoing/low-priority/group-summary, hide contents, only-while-locked) and de-duplicates updates. The Mac then applies its own per-app **show/hide** and **banner/silent** preferences, privacy mode and history size, and posts through UserNotifications (macOS Focus applies). Dismissing on either side sends `NOTIF_REMOVED` / `NOTIF_DISMISS` when "Dismiss on both" is on.

## 11. Privacy

Logs on both sides record events and sizes only, never clipboard text, notification content or file names. The Mac skips pasteboard items marked concealed or transient (nspasteboard.org conventions, used by password managers).

## 12. Revision 2 (app 0.2.0)

The handshake and record format are unchanged (`Hello.v` stays 1), so 0.1.x and 0.2.x still pair and sync. Each new feature is announced in `Hello.caps`, and a device only uses a feature the peer announced:

| Cap | Feature |
|---|---|
| `clip`, `notif`, `file` | 0.1.x features (also assumed when `caps` is missing) |
| `reply` | notification buttons and inline replies |
| `media` | automatic screenshots/photos (`FILE_OFFER.kind`) |
| `battery` | phone battery/network |
| `ring` | find my phone |
| `screen` | screen view and control |

Older builds ignore the new message types and the new optional JSON fields. A `Hello.v` other than 1 still closes with *version mismatch*.

### Additions to existing messages

- `NOTIF` gains `actions: [{"id","title","reply":bool}]` (at most 4; a reply action has a free-form RemoteInput on the phone).
- `FILE_OFFER` gains `kind`: `"screenshot"` or `"photo"` for automatic media; absent for a user's file. Photos are queued *Wi-Fi only*: they wait for the Wi-Fi session and never cross Bluetooth. The phone de-duplicates by SHA-256 and never sends media older than the moment the feature was turned on.

### New messages

| Type | Name | Direction | Header | Body |
|---|---|---|---|---|
| 0x43 | NOTIF_ACTION | Mac → phone | `{"key","action","text"?}` | |
| 0x44 | NOTIF_ACTION_RESULT | phone → Mac | `{"key","action","ok","reason"?}` (`gone`, `denied`, `empty`, `disabled`) | |
| 0x70 | BATTERY | phone → Mac | `{"level":0-100,"charging","plug"?,"net"?,"gen"?,"signal"?:0-4,"ts"}` | |
| 0x71 | RING | Mac → phone | `{"timeoutS":60}` (capped at 60 s) | |
| 0x72 | RING_STOP | either | `{"reason"}` | |
| 0x73 | RING_STATE | phone → Mac | `{"ringing","reason"?}` | |
| 0x80 | SCREEN_START | Mac → phone | `{"maxSize","fps","bitrate"}` (upper bounds) | |
| 0x81 | SCREEN_STATE | phone → Mac | `{"state","w","h","rotation","control","reason"?}`; state ∈ `consent`, `live`, `stopped`, `denied`, `needs_wifi`, `error` | |
| 0x82 | SCREEN_STOP | either | `{"reason"}` | |
| 0x83 | VIDEO_FRAME | phone → Mac, **Wi-Fi only** | `{"src":"screen","seq","pts"(µs),"key","config","part","parts"}` | H.264 Annex B access unit (or part of one) |
| 0x84 | SCREEN_INPUT | Mac → phone | `{"k","x","y","x2"?,"y2"?,"dur"?,"text"?,"rot"?}` | |
| 0x85 | VIDEO_FEEDBACK | Mac → phone | `{"src","kbps","lagMs","dropped","keyframe"}` | |

- **Battery** is pushed on change and throttled: charging/plug changes and reaching 20/10/5 % go at once, other changes at most once a minute, and an unchanged state is repeated every 10 minutes. The Mac alerts once at ≤ 20 % while not charging and re-arms after charging or > 25 %.
- **Screen**: SCREEN_START answers `needs_wifi` when only Bluetooth is up. Otherwise the phone asks the user (Android's capture consent, every session) and reports `consent`, then `live` with the encoded size and display rotation (sent again after every rotation, with new SPS/PPS). Every keyframe carries its SPS/PPS. Access units larger than 1 MiB are split into `parts` (same `seq`); the receiver drops an incomplete frame when a newer one starts and waits for the next keyframe. The phone adapts the bitrate from its socket backlog and VIDEO_FEEDBACK (×0.7 on congestion at most once a second, ×1.15 after 3 s calm at most every 2 s) and drops non-key frames when more than 768 KiB are queued.
- **Input** coordinates are normalised to the shown frame (0..1, origin top-left) and `rot` names the frame rotation they refer to; the phone maps them through the natural orientation to the current display, so a tap lands on the same physical spot even if the phone rotated in between. `k` ∈ `tap`, `long`, `swipe`, `scroll` (with `x2`,`y2`,`dur`), `text` (`text`), `backspace`, `enter`, `back`, `home`, `recents`.
- Video, input, feedback and screen control prefer the Wi-Fi session; everything else in this section prefers Bluetooth.
