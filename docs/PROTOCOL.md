# Tether protocol v1 (revision 3.1)

Tether links one Android phone and one Mac directly: no server, no account, no cloud.
Everything below is implemented twice, independently, and cross-checked with shared test vectors:

| | Android (Kotlin) | macOS (Swift) |
|---|---|---|
| Code | `android/core` | `mac/TetherCore` |
| Vectors | `protocol/vectors/*.json` (generated by `tools/gen_vectors.py`) | same files |

All integers are big-endian. "B64" means base64url without padding.

## 1. Roles and transports

- **Bluetooth LE (always on).** The phone is the GATT **central** (scans with a service-UUID filter and connects); the Mac is the GATT **peripheral** (advertises only while paired or pairing).
  - Service `7E7E0001-5A1D-4C6B-9C0E-7465746865B1`
  - One characteristic `7E7E0002-5A1D-4C6B-9C0E-7465746865B1`: phone → Mac by *write without response*, Mac → phone by *notify*.
  - The phone requests a 517-byte MTU; the fragment size is `min(MTU − 3, 512)` (minimum 20). **Never more than 512**: a GATT attribute value is at most 512 bytes and Android 13+ (`BluetoothGatt.writeCharacteristic`) throws for longer values even when the MTU allows 514 — the 0.3.0 phone did exactly that, wedging its write queue after the handshake (fixed in 0.3.1).
- **Wi-Fi fast path (optional).** When both devices share a network (or the Mac joins the phone's hotspot) the phone listens on TCP and advertises `_tether._tcp` over mDNS. It tells the Mac where to connect over the Bluetooth session (§6). Records on TCP are framed as `u32 length ‖ record` (max 2 MiB).
- In both cases the **phone is the Noise initiator** and the Mac the responder.

## 2. Fragments (Bluetooth only)

A record larger than one ATT payload is split into fragments (layout adapted from bitchat's fragment header):

```
u8  version = 1
u16 recordId      (wraps; one record in flight per direction)
u16 index         (0-based)
u16 total
…   data          (up to maxFragment − 7 bytes)
```

Both sides cap `maxFragment` at 512 bytes (header included). Fragments of a record arrive in order (the link is ordered). The reassembler drops a record on any gap, version mismatch, or if it would exceed 128 KiB; a fragment with `index = 0` always starts a new record.

## 3. Records

```
0x01 ‖ step ‖ noise_message      handshake (step = 1, 2, 3)
0x02 ‖ ciphertext                transport (ChaCha20-Poly1305, Noise nonce counter)
0x03 ‖ reason                    close (plaintext; reasons below)
```

Close reasons: `0 normal, 1 untrusted, 2 busy, 3 protocol error, 4 version mismatch, 5 pairing rejected, 6 unpaired, 7 wrong device, 8 timeout, 9 link lost`.

## 4. Handshake: `Noise_XX_25519_ChaChaPoly_SHA256`

- Prologue: `tether/1` on Bluetooth, `tether/1/wifi` on TCP (a Bluetooth handshake can't be replayed onto TCP or vice versa).
- Static keys: one X25519 key pair per install (Android Keystore-wrapped file / macOS Keychain).
- Payloads: message 1 is empty; messages 2 and 3 carry a JSON **Hello**:
  `{"v":1,"name":"Pixel 8","platform":"android","app":"0.1.0","caps":["clip","notif","file"]}`.
  A `v` other than 1 closes with *version mismatch*.
- After message 3 both sides hold the peer's static key. If it is the paired key (or a pending rotated key, §7) the session is **established**. Otherwise:
  - If pairing is not open on this device → close *untrusted*.
  - Otherwise the session enters **verifying** (pairing, §5).
- Heartbeat: `PING` every 45 s of silence, dead after 20 s more. Each path (Bluetooth, Wi-Fi) has its own heartbeat; on Bluetooth every received *fragment* counts as proof of life (since 0.3.1), so a long record in flight can't trip it. A Bluetooth reconnect while the Wi-Fi session is bound does not change the visible link state. Handshake timeout 15 s; pairing timeout 120 s.
- Handshake recovery (Bluetooth, since 0.1.1): if the phone hears nothing within 3 s of sending message 1, it starts a fresh session and sends a new message 1 (up to 3 times per link). The Mac starts a fresh session whenever a message 1 arrives while it is still handshaking or after its session closed with the radio link still up, so a lost write never wedges the link. Writes that reach the Mac before the phone's subscription is reported are held and replayed. Fragments are capped at 244 bytes (phone requests ATT MTU 247).

## 5. Pairing

Two ways, both on top of an unauthenticated XX handshake:

1. **Numeric comparison.** Both sides show `SAS = u32(SHA-256("tether-sas/1" ‖ handshake_hash)[0..4]) mod 10^6`, zero-padded to 6 digits. Each user confirms; each device sends `PAIR_CONFIRM {}`. Pairing completes when a device has both confirmed locally and received the peer's confirm. `PAIR_REJECT` (or a timeout) closes with *pairing rejected*.
2. **QR (one tap).** The Mac shows `tether://pair?v=1&k=<B64 Mac static key>&t=<B64 16-byte one-time token>&n=<percent-encoded name>`. The phone scans it, connects, and checks during the handshake that the Mac's static key equals `k` (else close *wrong device*). The phone then auto-confirms with `PAIR_CONFIRM {"token":"<t>"}`; the Mac accepts that as its own confirmation only if the token matches in constant time. The token dies when pairing mode closes.

Only one phone is paired at a time; pairing a new one replaces the old.

## 7. Key rotation

Either side may send `KEY_ROTATE` with a fresh public key over an established Bluetooth session. The receiver stores it as the peer's *pending* key (both old and pending are trusted) and answers `KEY_ROTATE_ACK`. On the ack the sender switches its static key; the next handshake uses the new key and the receiver promotes pending → current. An unacknowledged rotation is retried on the next connection.

## 8. Wi-Fi binding

1. Over the established Bluetooth session the phone sends `WIFI_OFFER` with its addresses, port and a single-use 16-byte token.
2. The Mac connects (Bonjour service whose TXT `id` = B64(SHA-256(phone static key)[0..8]) first, then each address), runs Noise XX with prologue `tether/1/wifi`, and must present **the paired static key**: there is no pairing on TCP.
3. The Mac's first transport message is `WIFI_BIND {token}`. The phone admits it in constant time and burns the token; anything else closes the socket as *untrusted*. A bound session that has not bound within 15 s is closed.
4. While Wi-Fi is bound, clipboard and transfers use it; notifications and control stay on Bluetooth. If Wi-Fi drops, transfers fall back to Bluetooth from the last acknowledged offset.

## 9. File transfer

- Sender stages the file, computes SHA-256, and sends `FILE_OFFER`. Receiver answers `FILE_ACCEPT {offset}` (0, or the length of a partial file from an earlier attempt) or `FILE_REJECT`.
- Sender streams `FILE_CHUNK`s (16 KiB on Bluetooth, 64 KiB on Wi-Fi) with a sliding window (4 chunks on Bluetooth, 16 on Wi-Fi) driven by cumulative `FILE_ACK`s.
- After the last byte, `FILE_DONE`; the receiver verifies SHA-256, moves the file into place, and answers `FILE_COMPLETE {ok}`. A checksum failure restarts once from 0, then fails.
- Limits: warn above 20 MiB; files above 100 MiB wait for Wi-Fi (up to 4 GiB). Interrupted transfers resume after reconnect or relaunch.
- File names are sanitised (no path separators, reserved or control characters, or leading dots; long names are shortened).

## 10. Notifications

The phone decides what to forward (per-app allow/block, muted keywords, quiet hours, skip silent/ongoing/low-priority/group-summary, hide contents, only-while-locked) and de-duplicates updates. The Mac then applies its own per-app **show/hide** and **banner/silent** preferences, privacy mode and history size, and posts through UserNotifications (macOS Focus applies). Dismissing on either side sends `NOTIF_REMOVED` / `NOTIF_DISMISS` when "Dismiss on both" is on.

## 11. Privacy

Logs on both sides record events and sizes only, never clipboard text, notification content or file names. The Mac skips pasteboard items marked concealed or transient (nspasteboard.org conventions, used by password managers).

## 12. Revision 2 (app 0.2.0)

The handshake and record format are unchanged (`Hello.v` stays 1), so 0.1.x and 0.2.x still pair and sync. Each new feature is announced in `Hello.caps`, and a device only uses a feature the peer announced:

| Cap | Feature |
|---|---|
| `clip`, `notif`, `file` | 0.1.x features (also assumed when `caps` is missing) |
| `reply` | notification buttons and inline replies |
| `media` | automatic screenshots/photos (`FILE_OFFER.kind`) |
| `battery` | phone battery/network |
| `ring` | find my phone |
| `screen` | screen view and control |

Older builds ignore the new message types and the new optional JSON fields. A `Hello.v` other than 1 still closes with *version mismatch*.

### Additions to existing messages

- `NOTIF` gains `actions: [{"id","title","reply":bool}]` (at most 4; a reply action has a free-form RemoteInput on the phone).
- `FILE_OFFER` gains `kind`: `"screenshot"` or `"photo"` for automatic media; absent for a user's file. Photos are queued *Wi-Fi only*: they wait for the Wi-Fi session and never cross Bluetooth. The phone de-duplicates by SHA-256 and never sends media older than the moment the feature was turned on.

### New messages

| Type | Name | Direction | Header | Body |
|---|---|---|---|---|
| 0x43 | NOTIF_ACTION | Mac → phone | `{"key","action","text"?}` | |
| 0x44 | NOTIF_ACTION_RESULT | phone → Mac | `{"key","action","ok","reason"?}` (`gone`, `denied`, `empty`, `disabled`) | |
| 0x70 | BATTERY | phone → Mac | `{"level":0-100,"charging","plug"?,"net"?,"gen"?,"signal"?:0-4,"ts"}` | |
| 0x71 | RING | Mac → phone | `{"timeoutS":60}` (capped at 60 s) | |
| 0x72 | RING_STOP | either | `{"reason"}` | |
| 0x73 | RING_STATE | phone → Mac | `{"ringing","reason"?}` | |
| 0x80 | SCREEN_START | Mac → phone | `{"maxSize","fps","bitrate"}` (upper bounds) | |
| 0x81 | SCREEN_STATE | phone → Mac | `{"state","w","h","rotation","control","reason"?}`; state ∈ `consent`, `live`, `stopped`, `denied`, `needs_wifi`, `error` | |
| 0x82 | SCREEN_STOP | either | `{"reason"}` | |
| 0x83 | VIDEO_FRAME | phone → Mac, **Wi-Fi only** | `{"src":"screen","seq","pts"(µs),"key","config","part","parts"}` | H.264 Annex B access unit (or part of one) |
| 0x84 | SCREEN_INPUT | Mac → phone | `{"k","x","y","x2"?,"y2"?,"dur"?,"text"?,"rot"?}` | |
| 0x85 | VIDEO_FEEDBACK | Mac → phone | `{"src","kbps","lagMs","dropped","keyframe"}` | |

- **Battery** is pushed on change and throttled: charging/plug changes and reaching 20/10/5 % go at once, other changes at most once a minute, and an unchanged state is repeated every 10 minutes. The Mac alerts once at ≤ 20 % while not charging and re-arms after charging or > 25 %.
- **Screen**: SCREEN_START answers `needs_wifi` when only Bluetooth is up. Otherwise the phone asks the user (Android's capture consent, every session) and reports `consent`, then `live` with the encoded size and display rotation (sent again after every rotation, with new SPS/PPS). Every keyframe carries its SPS/PPS. Access units larger than 1 MiB are split into `parts` (same `seq`); the receiver drops an incomplete frame when a newer one starts and waits for the next keyframe. The phone adapts the bitrate from its socket backlog and VIDEO_FEEDBACK (×0.7 on congestion at most once a second, ×1.15 after 3 s calm at most every 2 s) and drops non-key frames when more than 768 KiB are queued.
- **Input** coordinates are normalised to the shown frame (0..1, origin top-left) and `rot` names the frame rotation they refer to; the phone maps them through the natural orientation to the current display, so a tap lands on the same physical spot even if the phone rotated in between. `k` ∈ `tap`, `long`, `swipe`, `scroll` (with `x2`,`y2`,`dur`), `text` (`text`), `backspace`, `enter`, `back`, `home`, `recents`.
- Video, input, feedback and screen control prefer the Wi-Fi session; everything else in this section prefers Bluetooth.

## 13. Revision 3 (app 0.3.0)

Same rules as revision 2: `Hello.v` stays 1, features are announced in `Hello.caps`, and 0.2.x peers ignore everything here.

| Cap | Feature |
|---|---|
| `sms` | text-message conversations, search and sending |
| `call` | incoming-call alerts, Decline / Silence, missed calls |
| `nowplaying` | the phone's current media session and remote control |
| `proximity` | Bluetooth signal-strength reports for "lock when the phone walks away" |

### New messages

| Type | Name | Direction | Header | Body |
|---|---|---|---|---|
| 0x90 | SMS_THREADS_REQ | Mac → phone | `{"limit":50,"before"?:ms,"query"?}` | |
| 0x91 | SMS_THREADS | phone → Mac | `{"threads":[Thread],"more","query"?,"needs"?}` (`needs` = `sms` permission missing, `disabled`, or `error:<reason>` when the phone's store failed — 3.1) | |
| 0x92 | SMS_THREAD_REQ | Mac → phone | `{"thread","limit":60,"before"?:ms}` | |
| 0x93 | SMS_MESSAGES | phone → Mac | `{"thread","msgs":[Msg] (oldest first),"more","search"?,"error"?}` (`thread` = -1 for search results; `error` = `sms`, `disabled` or `error:<reason>` — 3.1) | |
| 0x94 | SMS_SEND | Mac → phone | `{"ref","to":[addr],"body","thread"?,"sub"?}` (`sub` = Android subscription id; absent = default SMS SIM) | |
| 0x95 | SMS_SEND_RESULT | phone → Mac | `{"ref","ok","reason"?}` (`needs_permission`, `no_service`, `radio_off`, `no_sim`, `limit`, `short_code`, `invalid`, `disabled`, `failed`) | |
| 0x96 | SMS_NEW | phone → Mac | `{"msg":Msg}`: a new message, or one of ours whose status changed | |
| 0x97 | SMS_SEARCH | Mac → phone | `{"query","limit":50}`, answered by SMS_MESSAGES with `search` | |
| 0x98 | SIMS | phone → Mac | `{"sims":[{"id","slot","name","number"?}]}` on connect and when SIMs change | |
| 0xA0 | CALL_STATE | phone → Mac | `{"id","state","number"?,"name"?,"ts","reason"?}`; state ∈ `ringing`, `offhook`, `ended`, `missed` | |
| 0xA1 | CALL_ACTION | Mac → phone | `{"id","action"}`; action ∈ `decline`, `silence` | |
| 0xB0 | NOW_PLAYING | phone → Mac | `{"active","pkg","app","title","artist","album","durationMs","positionMs","playing","speed","canSeek","canNext","canPrev","volume"?:0-1,"art"?,"ts"}` | |
| 0xB1 | MEDIA_CMD | Mac → phone | `{"cmd","pos"?:ms,"vol"?:0-1}`; cmd ∈ `play`, `pause`, `toggle`, `next`, `prev`, `seek`, `volume` | |
| 0xB2 | NOW_PLAYING_ART | phone → Mac | `{"hash"}` | JPEG ≤ 96 KiB (decoders accept ≤ 256 KiB) |
| 0xD0 | RSSI | phone → Mac | `{"rssi":dBm,"ts"}` | |
| 0xD1 | PROXIMITY_CFG | Mac → phone | `{"on","intervalMs":2000}` (phone clamps to 1–10 s) | |

`Thread` = `{"id","addrs":[..],"names":[name|null],"snippet","date","unread","outLast"}`.
`Msg` = `{"id" ("s<n>" SMS / "m<n>" MMS),"thread","addr","name"?,"body","date","out","status" (received|sent|pending|failed),"sub"?,"att":[{"id","mime","w","h"}],"read"}`.

- **SMS**: the phone reads the system SMS/MMS provider (it is not the default SMS app and never writes to it). Lists are trimmed so one message stays under ~60 KiB (`more` is then true and the Mac pages with `before`). The phone watches the provider and pushes SMS_NEW for new rows and for its own pending rows when they become sent/failed. Android records messages Tether sends, so they come back as SMS_NEW; the Mac replaces its placeholder with that copy. MMS text is included; attachments are listed (`att`) but their data is not transferred in revision 3.
- **SMS reliability (3.1)**: every SMS_THREADS_REQ, SMS_THREAD_REQ and SMS_SEARCH gets exactly one answer, including on failure (`needs`/`error`). The phone reads the threads table (`content://mms-sms/conversations?simple=true` + canonical addresses) in one bounded query and falls back to a bounded scan of `content://sms`/`content://mms`; it answers within ~6 s. SMS_THREADS, SMS_MESSAGES and NOW_PLAYING_ART prefer the Wi-Fi session when it is bound. The Mac gives up on a request after 15 s and offers Retry, and re-sends open requests after a reconnect. An authenticated message whose header can't be decoded is dropped and logged (`msg.decode_failed`) instead of closing the session.
- **Calls**: `ringing` may be sent more than once for one `id` as the number or name becomes known. A call that rang and went idle without being answered is `missed` (unless the Mac declined it, then `ended`). Outgoing calls are never reported. A failed CALL_ACTION is answered with the current state plus `reason` (`not_allowed`, `needs_dnd_access`, `no_call`).
- **Now playing**: sent at once on track/state changes (at most every 300 ms) and re-sent every 15 s; the Mac extrapolates the position from `positionMs`, `speed` and `ts`. Artwork is sent once per hash per connection.
- **Proximity**: the Mac turns reports on with PROXIMITY_CFG only while its lock feature is enabled; the phone reads the GATT link RSSI (`BluetoothGatt.readRemoteRssi`). Smoothing, thresholds, hysteresis and the dwell time are decided on the Mac (see `Proximity.swift`); losing the Bluetooth link after the phone was known to be near counts as away. The Mac never unlocks.

## 14. Revision 4 (app 0.4.0)

Same rules again: `Hello.v` stays 1, every feature is announced in `Hello.caps`, and a side only sends a revision-4 message (or a new CALL_ACTION action) when the peer announced the matching cap. 0.3.x builds decode the new types as unknown and ignore them (checked in CI against the released 0.3.1 Swift core), and ignore the new optional JSON fields.

| Cap | Feature |
|---|---|
| `dial` | the Mac places calls through the phone (CALL_DIAL / CALL_DIAL_RESULT), contact search (CONTACT_SEARCH / CONTACTS); SIMS is also sent for calling |
| `callctl` | the live call card (CALL_LIVE) and the CALL_ACTION actions `answer`, `end`, `speaker`, `mute`, `hold` |
| `calllog` | call history (CALL_LOG_REQ / CALL_LOG) |
| `notifaccess` | Android 15+ sensitive-notification status (NOTIF_ACCESS) |

### Additions to existing messages

- **CALL_ACTION** (0xA1) gains optional `"on"` (for `speaker` / `mute` / `hold`) and `"speaker"` (for `answer`: turn the phone's speaker on once the call is up). Both are omitted when absent, so the header a 0.3 phone receives for `decline` / `silence` is byte-for-byte the 0.3 one.
- **SIMS** (0x98) is sent on connect when the Mac announced `sms` *or* `dial` (and the matching feature is on), so the dial pad can offer the SIM picker.

### New messages

| Type | Name | Direction | Header | Body |
|---|---|---|---|---|
| 0x45 | NOTIF_ACCESS | phone → Mac | `{"redacting","granted"?,"sdk","oem","ts"}`: `redacting` = Android replaced a notification's text with its "Sensitive notification content hidden" string since access was last granted; `granted` = the `RECEIVE_SENSITIVE_NOTIFICATIONS` app op is allowed (absent when the phone can't tell) | |
| 0xA2 | CALL_DIAL | Mac → phone | `{"ref","number","sub"?}` (`sub` = subscription id; absent = the phone's default) | |
| 0xA3 | CALL_DIAL_RESULT | phone → Mac | `{"ref","ok","reason"?,"via"?}`; `via` ∈ `telecom` (call placed), `notification` (the phone needs a tap); `reason` ∈ `needs_permission`, `disabled`, `invalid_number`, `no_sim`, `busy`, `emergency`, `no_call`, `failed` | |
| 0xA4 | CALL_LIVE | phone → Mac | `{"id","dir" (in\|out),"state" (ringing\|dialing\|active\|ended),"number"?,"name"?,"since":ms,"speaker","muted","held","canAnswer","canEnd","canSpeaker","canMute","canHold","sub"?,"ts","reason"?}` | |
| 0xA5 | CALL_LOG_REQ | Mac → phone | `{"limit":50,"before"?:ms}` | |
| 0xA6 | CALL_LOG | phone → Mac | `{"calls":[Call] (newest first),"more","needs"?,"before"?}` (`needs` = `calllog` permission, `disabled`, `error:<reason>`; `before` echoes the request) | |
| 0xA7 | CONTACT_SEARCH | Mac → phone | `{"query","limit":20}` | |
| 0xA8 | CONTACTS | phone → Mac | `{"query","contacts":[{"name","numbers":[{"n","label"?}]}],"needs"?}` (`needs` = `contacts`, `disabled`, `error:<reason>`) | |

`Call` = `{"id","number","name"?,"type" (in|out|missed|rejected|blocked|voicemail|other),"date":ms,"dur":s,"sub"?,"isNew"}`.

- **Dialing**: the phone cleans the number (digits, leading `+`, `*`, `#`, `,` pause, `;` wait; anything else → `invalid_number`), refuses emergency numbers (dial those on the phone) and places the call with `TelecomManager.placeCall` (CALL_PHONE). That is a call into the system telecom service, not an activity start, so it works while Tether runs in the background on Android 10–16. CALL_DIAL_RESULT is sent when the phone goes off-hook (`ok`, `via:"telecom"`), or after 12 s without a call (`no_call`); if Telecom throws, the phone posts a "Tap to call" notification (`via:"notification"`). One dial at a time (`busy`).
- **Live call**: CALL_LIVE is sent on every change and once on connect while a call is up. `since` is the phone's clock when the call went off-hook (0 while ringing); for outgoing calls Android doesn't tell other apps when the far end answers, so the timer starts at dialing. `can*` say which controls work right now: Answer needs ANSWER_PHONE_CALLS, End needs it on Android 9+, Speaker / Mute use AudioManager and are verified by reading the state back — when Android ignores them the phone clears the flag and reports `reason:"unsupported"`, so the Mac hides the control. Hold needs the default-dialer role and is never offered by Tether. Older Macs keep getting the revision-3 CALL_STATE events exactly as before (incoming calls only).
- **Call audio** always stays on the phone or the earbuds connected to it: Android has no API for an app to route cellular call audio to another device.
- CALL_LOG and CONTACTS prefer the Wi-Fi session (like SMS lists); lists are trimmed to stay under ~48 KiB (`more` is then true).
- A Call's `number` is display-formatted by the phone (grouped the way contacts show numbers, e.g. `+91 98470 12345`); match and dial on its digits only.

| 0xC8 | CONTINUE | phone → Mac | `{"id","kind" (photo\|download\|link\|share\|song\|tab),"title","subtitle"?,"url"?,"root"?,"path"?,"app"?,"size","ts","ttl":900}` | optional JPEG thumbnail |
| 0xC9 | OPEN_ON_PHONE | Mac → phone | `{"id","url"?,"text"?}` (url schemes the phone opens: http, https, mailto, tel, geo, sms, smsto, market, spotify, upi; others → `reason:"invalid"`) | |
| 0xCA | OPEN_RESULT | phone → Mac | `{"id","ok","via"? (activity\|notification),"reason"?}` | |
| 0xCB | TYPE_TEXT | Mac → phone | `{"seq","text"?,"key"? (backspace\|enter\|tab\|clear)}` | |
| 0xCC | TYPE_RESULT | phone → Mac | `{"seq","ok","reason"? (no_field\|accessibility\|disabled\|…),"field"?}` | |
| 0xE0 | DND_STATE | both | `{"on","src" (phone\|mac),"ts","canSet"?}` | |
| 0xE1 | PHONE_STATUS | phone → Mac | `{"perms":[{"id","label","ok","required"}],"sdk","ts"}` | |
| 0xE2 | PHONE_STATUS_REQ | Mac → phone | `{"ts"?}` | |

- **Roots**: `downloads`, `documents`, `whatsapp`, `dcim`, `pictures` (paths relative to the root; the phone canonicalises every path and refuses anything that leaves the root) and `photos` (MediaStore id as the path). Listings and thumbnails prefer the Wi-Fi session; lists are trimmed to stay under ~48 KiB (`more` true).
- **Transfer kinds**: `screenshot` / `photo` (rev 2) are automatic media and go to the media folder; `fs` (a file the Mac asked for) goes to the download folder or the folder the user dragged it to; `clip` is a clipboard image: the receiver puts it on its clipboard and hides it from the transfer list. Receivers of rev ≤ 4 treat unknown kinds as ordinary files.
- **OTP** is extracted on the phone (OtpDetector, unit-tested against real bank/app message formats; amounts, dates and reference numbers are excluded) from incoming SMS and mirrored notifications; the same code is sent once (deduplicated on the phone).
- **DND echo guard**: each side ignores a state equal to the one it just applied for 4 s (DndSync), so Focus ↔ DND never ping-pongs.
- **Continue cards** expire after `ttl` seconds (min 30); the Mac keeps at most 8 and remembers dismissed ones.
- Updates are not part of the protocol: each app reads GitHub releases itself (README › Updates).

## 16. Revision 5.1 (app 0.5.1)

One new cap, `albums`, announced by 0.5.1 builds. Without it nothing below is sent; 0.5.0 peers decode the new optional fields as unknown keys and ignore them.

| Type | Name | Direction | Header | Body |
|---|---|---|---|---|
| 0xCD | ALBUMS_REQ | Mac → phone | `{"ref"}` | |
| 0xCE | ALBUMS | phone → Mac | `{"ref","albums":[{"id","name","count","cover"?,"kind"}],"needs"?}` | |

- **Album ids / kinds**: `all`, `camera` (DCIM/Camera), `screenshots`, `whatsapp` (WhatsApp Images), `downloads`, `videos`, `favorites` (MediaStore `IS_FAVORITE`, Android 11+, listed only when it has items), then `b:<bucketId>` for every other MediaStore bucket, biggest first. `cover` is the newest item's MediaStore id (THUMB_REQ root `photos`).
- **PHOTOS_REQ** gains `"album"?` (an album id, absent = all) and `"filter"?` (`photos` | `videos` | `screenshots`). Default page size from the Mac is 90.
- **PhotoItem** gains `"dur"` (video duration, ms), `"bucket"?` and `"fav"`.
- **TYPE_RESULT** `reason` adds `no_service` (Tether control is off in Accessibility) and `binding` (it is on but not bound yet). The Mac times out a batch with no answer after 4 s and says so.
- **OPEN_ON_PHONE** with `url` = `tether://setup/<id>` opens the fix for that checklist row on the phone (its Settings screen, or a tap-to-open notification when Tether may not start activities from the background). The Mac's "Fix" buttons use it.
- **Clipboard images**: both sides classify a copy before sending it. An image (including a Finder-copied image file, or a gallery clip that carries the image URI plus its file name as text) goes as a `clip` transfer; a copied non-image file sends nothing; only plain text goes as CLIP.
